## 1. Problem Statement

バンドのスタジオ練習日程を決めるとき、リーダーは各メンバーから個別に「この日なら入れる」という情報をテキスト（LINE/メッセージ等）で受け取り、頭やメモで突合して共通の空き日程を抽出し、さらにスタジオの空き状況と照合する必要がある。この一連の作業は手間がかかり、予定変更があるたびにやり直しになる。

### Who is affected?
- **バンドリーダー**: 全員の予定を集約・突合する役割を担い、最も負担が大きい
- **バンドメンバー**: 自分の予定を伝え、何度も候補日を確認するやりとりが発生する

### What is the current experience?
1. リーダーがメンバー全員に「いつ空いてる？」と聞く
2. 各メンバーがバラバラのフォーマットで返信（「来週の火曜以外OK」「土日午後なら」など）
3. リーダーがテキストを読み解いて共通の空き時間を割り出す
4. スタジオに電話/Webで空き状況を確認
5. 候補日を再度メンバーに共有して合意形成
6. 予定変更があれば 1 からやり直し

### Why now?
- 自分が所属するバンドで実際に発生している不便を解消したい
- 個人プロジェクトとして実装の自由度が高く、技術的にも学びがある
- 将来的には事務所等に所属していない地方の独立系バンドに展開できる可能性がある

## 2. Goals & Success Metrics

### Goals
1. メンバー全員が空いている時間帯を、カレンダー/タイムラインで一目で可視化する
2. 予定入力の負担を最小化する（空き時間ベース/不可時間ベースの2モード対応）
3. スタジオ予約は外部（電話）で行う前提で、予約判断に必要な情報をスムーズに参照できる状態にする

### Success Metrics
個人開発のため明示的な定量指標は設定しない。定性的なゴールとして以下を意識する。

| 観点 | 期待する状態 |
|------|------------|
| 操作負荷 | 予定入力が数タップで完了する |
| 可視化 | 共通空き時間が画面を開いて2秒以内に把握できる |
| 継続利用 | 自バンドのメンバーが日常的に使い続ける |

### Non-Goals
- スタジオ予約APIとの自動連携（スタジオ側がAPIを提供していないことがほとんど）
- スタジオの自動予約機能（電話必須のスタジオが多いため）
- 複数バンド同時運用のマルチテナント機能（直近は自バンドのみ）
- スタジオのレビュー・評価機能
- メンバー以外のゲスト共有機能（初期版では不要）

## 3. User Stories

### Primary User: バンドメンバー（リーダー含む）

**Story 1:** バンドメンバーとして、自分の空き時間（または不可時間）をスマホからサッと入力したい。練習や本番が近いとき、移動中でも素早く入力できるとよい。

**Story 2:** バンドメンバーとして、自分が予定を入力した時点で「他のメンバーと共通で空いている時間帯」がすぐ見えると、そのまま「この日いけそう」と提案できる。

**Story 3:** バンドメンバーとして、入力モードを「空いている時間ベース」と「空いていない時間ベース」で切り替えたい。普段忙しい人は「空いている時間」を入力する方が楽で、たまに予定が入る人は「空いていない時間」を入力する方が楽。

### Primary User: バンドリーダー

**Story 4:** バンドリーダーとして、月単位/週単位で全員の空き状況を俯瞰し、共通空き時間を特定したい。

**Story 5:** バンドリーダーとして、共通空き時間が見つかったら、その情報をもとにスタジオに電話して予約し、確定した練習予定をアプリに登録したい。

## 4. Proposed Solution

### 4.1 Solution Overview
Flutter製のWebアプリケーションとして実装する。バンドメンバーが自分の予定を入力すると、全員の予定が集約されてカレンダー/タイムラインビューに表示され、共通の空き時間が視覚的に強調される。スタジオ予約は外部（電話/Webサイト）で行う前提で、アプリは「いつ全員空いているか」を即座に把握することに特化する。

### 4.2 Key Features

1. **予定入力モード切り替え**
   - 空き時間ベース: 「この時間なら空いてる」を登録
   - 不可時間ベース: 「この時間は無理」を登録
   - メンバーごとにデフォルトモードを選択可能

2. **共通空き時間ビュー**
   - メンバー全員が空いている時間帯をカレンダー上で強調表示
   - 一部メンバーのみ空いている時間は別の表示でフォールバック（誰が空いている/空いていないか把握できる）

3. **カレンダー/タイムラインビュー**
   - 月単位ビュー: 日付ごとの空き状況を俯瞰
   - 週単位ビュー: 時間帯まで含めた詳細
   - メンバー別の予定を重ねて表示

4. **メンバー管理**
   - バンド単位でメンバーを登録・管理
   - 初期版ではバンドは1つ固定（自バンドのみ）

5. **練習予定登録**
   - 確定した練習予定（スタジオ・日時・メモ）をアプリに記録
   - 過去の練習履歴として参照可能

### 4.3 User Flow

#### 予定入力フロー（メンバー）
1. メンバーがログイン
2. 予定入力画面で入力モード（空き/不可）を選択
3. カレンダー上で日付/時間帯をタップして登録
4. 登録結果が他メンバーにも反映される

#### 練習予定決定フロー（リーダー）
1. リーダーが共通空き時間ビューを開く
2. 全員空いている時間帯から候補を選ぶ
3. スタジオに電話で空き状況を確認
4. 予約完了後、アプリに「練習予定」として登録
5. 他メンバーに練習予定が共有される

### 4.4 Edge Cases & Error Handling

| Scenario | Expected Behavior |
|----------|------------------|
| 全員の共通空き時間が存在しない | カレンダーに「共通空き時間なし」を明示。最も多くのメンバーが空いている時間帯を代替候補として提示 |
| 一部メンバーが予定未入力 | 「未入力メンバーあり」のラベルを表示し、入力済みメンバーのみで仮の共通空き時間を計算 |
| 過去日付の予定 | 編集不可（参照のみ）。過去の練習履歴として保持 |
| メンバーが同時編集 | 後勝ち更新。タイムスタンプを表示してコンフリクトを検知できるようにする |
| ネットワーク切断 | 入力をローカルにキャッシュし、復旧時に同期 |

## 5. Technical Considerations

### Architecture Impact
新規プロジェクトのため既存システムへの影響なし。スタックは Firebase 一括構成で確定。

- **Frontend**: Flutter Web（指定要件）
- **Backend**: Cloud Firestore（無料枠1GB保存、1日5万R/W、Flutter公式SDK対応）
- **Auth**: Firebase Authentication（無料、認証フローは**メールリンク方式**を採用 — パスワード管理不要・Googleアカウント非依存）
- **Hosting**: Firebase Hosting（無料枠10GB/月、SSL自動付与、CLIデプロイ）

### Dependencies
- Flutter SDK — 利用可能
- Firebase プロジェクト作成 — 要セットアップ
- `firebase_core` / `cloud_firestore` / `firebase_auth` Flutter パッケージ — 公式提供あり

### Technical Risks

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| Flutter Webのバンドルサイズが大きく初回ロードが遅い | M | M | 必要に応じてLazy LoadingやTree Shakingを活用、CDN経由で配信 |
| バックエンド料金が想定外に高くなる | L | M | 利用量を監視、無料枠内で収まる構成を初期版で選択 |
| データモデルの設計ミスで後から拡張が困難になる | M | M | 将来のマルチテナント化を意識し、`band_id` を最初からキーに含める |
| 認証実装の複雑化 | L | L | 初期はマジックリンク等のシンプル実装に絞る |

### Performance Requirements
- 月単位ビューの表示は2秒以内
- 予定入力後の他メンバーへの同期は3秒以内
- 同時接続メンバー数は10名程度を想定（初期版）

### Data Model（概略）

Firestore のサブコレクション構造で設計。`band_id` を最上位キーに置くことで、初期版から将来のマルチテナント化までシームレスに対応できるようにする。MVP段階では `band_id = "default"` 固定で1バンドのみを運用する想定。

#### コレクション構造

```
bands/{bandId}
  ├─ name: string                       # バンド名
  ├─ leader_uid: string                 # リーダーのFirebase Auth uid
  ├─ member_uids: string[]              # メンバーのuid一覧（セキュリティルール判定に使用）
  ├─ created_at: timestamp

bands/{bandId}/members/{uid}
  ├─ display_name: string               # 表示名
  ├─ email: string                      # メールリンク認証用
  ├─ default_input_mode: 'available' | 'unavailable'
  ├─ joined_at: timestamp

bands/{bandId}/busy_slots/{slotId}
  ├─ member_uid: string                 # 予定の所有者
  ├─ start_at: timestamp                # 不可時間の開始
  ├─ end_at: timestamp                  # 不可時間の終了
  ├─ source_input_mode: 'available' | 'unavailable'  # どちらのUIモードで入力されたか（監査用、計算には使わない）
  ├─ created_at: timestamp
  ├─ updated_at: timestamp

bands/{bandId}/practices/{practiceId}
  ├─ start_at: timestamp                # 練習開始時刻
  ├─ end_at: timestamp                  # 練習終了時刻
  ├─ studio_name: string                # スタジオ名（自由記述）
  ├─ memo: string                       # 備考
  ├─ created_by: string                 # 登録者uid
  ├─ created_at: timestamp
```

#### エンティティ関係

| Entity | 関係 |
|--------|------|
| `Band` | 1 バンドにつき複数の `Member`、`BusySlot`、`Practice` を持つ |
| `Member` | `Band` のサブコレクション。Firebase Auth の uid をドキュメントIDに採用 |
| `BusySlot` | メンバーの**不可時間**を表す。`member_uid` で `Member` を参照。1メンバーが複数件登録できる。記録のない時間は「空き」とみなす |
| `Practice` | バンド単位で1件の確定予定を表す。`Member` 参照は `created_by` のみ |

#### UI 2モードと内部表現の対応

UIでは2モード入力を提供するが、データは常に「不可時間（busy_slots）」として正規化して保存する。これにより共通空き時間の計算が一意なロジックで完結する。

| UIモード | 入力例 | 内部での保存 |
|---------|--------|-------------|
| **不可時間モード** | 「火曜13:00-17:00 は不可」 | `busy_slots` に1件: `{ start: 火 13:00, end: 火 17:00 }` をそのまま保存 |
| **空き時間モード** | 「火曜13:00-17:00 のみ空き」 | 対象日（火曜00:00-24:00）から空き時間を引いた残りを保存。`busy_slots` に2件: `{ start: 火 00:00, end: 火 13:00 }` と `{ start: 火 17:00, end: 火 24:00 }` |

「対象範囲」のデフォルトは**入力対象日の 00:00-24:00**。MVPでは日単位での変換に固定し、週単位や複数日選択は将来検討。

`source_input_mode` フィールドはどちらのUIで入力されたかを記録するが、共通空き時間の計算ロジックでは参照しない（あくまで監査・編集UI復元のための情報）。

#### 共通空き時間の計算方針

- MVP段階ではクライアント側で計算（メンバー10名規模なら十分高速）
- 表示する期間（例: 当月）の `busy_slots` を全メンバー分取得
- アルゴリズム: `全メンバーの busy_slots の和集合 → 対象期間からその和集合を引いた残り = 共通空き時間`
- メンバーが「予定未入力」の場合は計算対象から除外し、「未入力メンバーあり」のラベルを表示
- 将来的にメンバー数が増えた場合は Cloud Functions での事前集計を検討

#### セキュリティルール方針

- `bands/{bandId}` 配下の読み書きは `member_uids` に含まれる uid のみ許可
- `busy_slots` の書き込みは自分の `member_uid` のスロットのみ許可
- `practices` の書き込みはバンドメンバーなら誰でも可能（リーダー縛りはしない）
- 詳細ルールは実装着手時に Firestore Security Rules で記述

#### インデックス方針

- `busy_slots` は `start_at` の昇順で範囲クエリするためコンポジットインデックスを設定
- `practices` は `start_at` の昇順で取得

## 6. Design & UX

### Key UX Principles
- **モバイルファースト**: バンドメンバーはスマホでの入力が中心
- **タップ操作中心**: テキスト入力を最小化し、カレンダー上の選択で完結させる
- **視覚的な共通空き時間**: 色分けで「全員OK」「一部OK」「NG」を直感的に把握できる
- **ダークモード対応**: 移動中やライブ前の暗所でも見やすく

### Accessibility Requirements
- カラーブラインド対応: 色だけに頼らず、アイコンやパターンも併用
- フォントサイズ調整に対応
- スクリーンリーダー読み上げに配慮した構造（初期版では努力目標）

## 7. Release Strategy

### Rollout Plan
- **Phase 1 (MVP)**: 自バンド向けプライベート利用版
  - メンバー登録、予定入力（空き/不可の2モード）、共通空き時間ビュー、練習予定登録
  - 認証はメールリンク方式
  - スコープ外: 通知機能、スタジオ情報メモ、繰り返し予定
- **Phase 2**: 機能拡張と入力負担の削減
  - **通知機能**（共通空き時間検出・練習予定確定時のPush/メール通知）
  - **スタジオ情報メモ**（候補スタジオの連絡先・営業時間・料金などをアプリ内に保存）
  - **繰り返し予定**（毎週火曜は不可、など定期的な予定の一括登録）
- **Phase 3 (将来)**: 独立系バンド向けマルチテナント展開
  - バンド作成・参加機能、招待リンク、プラン分け検討

### Feature Flags
個人開発のため初期版ではフィーチャーフラグなし。Phase 3で導入を検討。

### Rollback Plan
個人プロジェクトのため、不具合時はホスティング側で前バージョンに切り戻し。データバックアップは定期的に取得。
